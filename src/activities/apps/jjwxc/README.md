# 晋江文学城

CrossMux 的非官方晋江文学城（JJWXC）客户端，用于账号登录、浏览个人书架与搜索作品，并按章增量缓存正文、打包成一个 EPUB 供内置阅读器离线阅读。

## 功能与使用

- 统一固件始终编译；仅在 China 内容区域显示。
- 从 **Apps → 晋江文学城** 进入。首次进入先显示免责声明，选择“同意”后才会联网；返回则退出到 Apps。已接受过的记录保存在 SD 卡，不因固件升级重复询问。
- 首页提供 **在线书架 / 搜索 / 已下载 / 账号** 四个入口。
- 账号页提供 **用上次账号登录 / 输入账号登录 / 退出登录 / 清除已保存的账号**（后两项按状态出现）。登录时在键盘之后询问一次保存范围：**不保存 / 仅保存账号 / 保存账号和密码**，选择会被记住作为下次的默认项。存了密码时「用上次账号登录」直接登录，不再弹键盘；只存了账号时仍会要求输入密码。
- **退出登录只清除会话 token，不动已保存的账号**；要把登录名和密码从本机去掉，必须显式选择「清除已保存的账号」。
- 登录按 **账号 → 密码 → 保存范围 → 登录** 顺序进行。服务端返回需要设备验证（状态码 `221003`）时，固件自动申请设备验证码并提示输入，随后重试同一次登录；不要求用户手工区分两种流程。保存范围只在登录**成功后**才落盘，密码打错不会把错的存下来。
- 在线书架列出账号已收藏的作品；搜索按书名／作者返回结果。两者都只做流式解析，不在内存中保存整份列表。
- 选择作品后进入详情页，提供 **缓存章节 / 章节列表 / 打开本地副本 / 刷新缓存** 四个动作。「打开本地副本」只在真有可读章节时出现——一本全是「本章未购买」占位的书不该占书架位。折叠状态下确实藏起了内容时，动作行最前面还会多出一行 **简介（显示／隐藏）**，它排在第一位而不是最后一位：折叠态只保证前两行动作在屏内，藏在需要滚动才看得到的位置的「展开」等于没有。缓存范围用预设选择：**整本 / 前 N 章 / 未缓存部分 / 重试未购买章 / 自定义起止**；键盘输入的是章节**序号**（第几章），不是 chapterId。
- **详情页版面**：左侧封面缩略图（`cover.thumb.bmp`，无缩略图但已知封面 URL 时画主题自带的占位框），右侧是事实行（作者／栏目／章节数／已缓存／未购买／字数／VIP 起始章／最新章／更新日期／标签），下方是**按行折叠的文案**（`novelIntro`），再下面才是动作行。三块的高度由同一个 `detailLayout()` 算出并被缓存（每次进入状态、每次展开／折叠时失效，绝不逐帧重算），`rowTop()`／`visibleRows()` 与绘制读的是同一份数字——这正是仓库规则 #14 要求的「绘制与命中测试同源」。
  - **栏目和标签会折行**，规则在纯头文件 `JjwxcTextWrap.h` 里（不含渲染器依赖，主机测试 `cpyos/src/JjwxcTextWrapTest.cpp` 与固件跑的是同一份代码）：标签只在分隔符处断（空格／逗号／`、`／`，`等），一个标签绝不会被劈成两半；栏目在 `-` 之后断，没有 `-` 时退化为按码位断；任何情况都不会切断一个 UTF-8 序列，超宽的单块按码位硬断而不是溢出列宽。其余事实行仍是一行、超宽裁剪，与改造前一致。
  - **折叠是算出来的，不是猜的**：`budget = 视口高 - 保留的动作行高 - kInfoBlockGap`（视口下边界取主题安全区与 `renderer.getScreenHeight()` 的较小者，绝不写死 1216），封面、事实行、文案依次从这个预算里扣，所以 `L.height + 保留行高 <= 视口高` 是构造性成立的——这就是「动作行一定在首屏」的全部依据。保留行数是 `min(动作行数, kDetailRowsReserve=2)`：首行与（尽量）第二行。事实行折行后可能比整块面板还高（实测一本书 16 行），此时折叠态会把事实列裁到预算内并在最后一行加省略号，文案行数为 0；**裁掉的部分不是丢了，展开就在**。
  - **展开** 后文案取全部折行高度、事实列不再裁剪，整页（信息块 + 动作行）由 `detailScroll_` 一起滚动：滑动或长按上／下键翻页，单击上／下键仍移动动作行选中并由页面跟随。`detailScroll_` 上限是 `min(块高, 溢出量)`，因此 `rowTop()` 永远不会跑到 `listTop()` 之上——`renderRows()` 的裁剪与 `rowTouch()`「`y < top` 不算命中一行」都还站在它们当初被写出来时的几何假设上。展开时点一下会把 `detailScroll_` 直接放到文案标题处，否则一整列事实挡在前面，用户看不到自己刚点开的东西。折叠／展开都从缓存失效开始，滚动位置一律重新夹取，不会把用户留在超出末尾的偏移上。
  - 文案来自 `novelbasicinfo` 的 `novelIntro`（实测 928 字／1,868 UTF-8 字节，含 40 个 `&lt;br/&gt;`、**一个真换行都没有**）。它不进 `NovelInfo`——那会让一个几 KB 的定长数组常驻内部 RAM——而是经 `NovelIntroSink` 交给 `intro_`（`jjwxc::PsramString`，PSRAM，上限 8 KB 且按码位截断）。反转义复用 WAP 正文那条链的 `wapDecodeEntities` + `wapHtmlToText`（原地、不增长、已在镜像内，**零额外 Flash**），所以没有第三套 HTML 处理代码。
  - `novelIntroShort` 是作者的一句话简介，**不是** `novelIntro` 的摘要（实测 13 字 vs 928 字）。两者都有时它作为文案的第一段；只有它时它就是文案；都没有时整个「简介」段不画。
  - 详情页与来源无关：从搜索结果打开和从书架打开走的是同一个 `openBook()`，`novelbasicinfo` 匿名可得，所以两边拿到的元数据完全一样。
- **未购买章节**：VIP 正文走 WAP，服务端对未购买的章直接拒绝——真机实测是 `302 → /buy/<novelId>/<chapterId>`，只是把请求引到购买页，**不会购买任何东西**。因此固件里不再有「自动购买策略」：早期那套三值策略（每次询问／允许自动购买／遇到未购买即停止）、它挡在第一个请求之前的征求同意弹窗、以及 `/.crosspoint/jjwxc/autobuy` 都已删除——它保护的是一件在这条路径上不可能发生的事，而其中的 `Stop` 还会在第一个未购章截断整本缓存（实测 197 章的书只进了 20 章免费章，176 章根本没被请求，包括用户**已经买过**的）。
  - 唯一保留下来的保护按**取正文走的路径**判定，不再按用户偏好：只有 App API（`chapterContent`，仅当目录的 `isVip` 过期、把一章真的付费章当成免费章请求时才会走到）上的购买拒绝才结束作业——那条路径上「请求」本身就会触发账号侧的自动订阅（实测 `code=1013`「余额不足，自动购买失败」、字符串 `"1010"`「已订阅或交易处理中」）；WAP 的拒绝一律写占位并继续。
  - 这条判定是库里的纯函数 `jjwxc::refusalEndsRun(verdict, servedFromWap)`（`lib/JjwxcApi/src/JjwxcProtocol.{h,cpp}`），固件与主机测试 `src/JjwxcUnpurchasedTest.cpp` 调的是同一个函数，所以测试钉住的是真规则而不是它的副本。作业结束时状态仍是成功：占位照写、书照打包，汇总里说明停在第几章。
- 未购买章**不计入「已缓存」**。`toc.bin` 里它是独立状态，成品 EPUB 中是一页说明占位（阅读器目录里标题带「（未购买）」后缀），但所有「已缓存 N」的口径都只数真正有正文的章。这正是之前「所有章节都已缓存」的来源：旧口径把占位也算了进去。
- 下载页分两段：先按章下载，显示已完成／总章数、累计字节数与**跳过数**；再打包图书，显示已入包章数。全程可取消，取消在章节边界生效，已落盘章节保留。
- 每次缓存结束都会给出汇总（已缓存 N/M · 未购买 K · 本次新增 J · 跳过 S），不再静默返回上一页。「缓存并阅读本章」会真的跳到那一章：固件在交给阅读器前写入 `progress.bin` 的 spine 序号，否则阅读器会恢复上次读到的位置，点第 50 章却回到第 120 章。
- 一部作品只对应一个固定路径的成品：`/JJWXC/<书名>-<novelId>.epub`。单章「缓存并阅读」、范围缓存、整本缓存都写入同一路径，不会产生第二个文件，因此「最近阅读」里一部作品只有一条记录。
- 章节列表逐章标示 **已缓存 / 未缓存 / 未购买 / 已锁定** 与是否 VIP，并允许非连续缓存（跳章）。成品 EPUB 只包含卡上真实存在的章节，缺章会让书变短，不会留下指向缺失文件的空引用。
- 已下载页可断网打开任意本地作品，交给内置阅读器；打开前会释放 TLS 会话，避免边读卡边持有连接造成堆碎片。目录已在卡上时，断网也能进入详情页与章节列表并从已缓存章节重新打包。
- **刷新缓存** 是显式动作，需要二次确认，确认文案会提示这会重新请求此前被服务端拒绝的章节。成品 EPUB 已存在**不会**触发全量重拉。刷新确认只对紧接着的那一次范围选择生效，不会残留成后续每次点击都全量重下。


## 协议选择

固件走 **Android App API**，不走 `m.jjwxc.net` 的 WAP 页面。原因是可验证的、而非偏好：

| | App API（本实现） | WAP 页面 |
|---|---|---|
| 编码 | UTF-8 JSON | GBK HTML |
| 正文洁净度 | 无替换字符、无零宽字符 | 存在 PUA 字体替换（U+E000–F8FF）与 `&zwnj;` 零宽字符 |
| 反爬水印 | 未观察到 | CSS `content:` 文字位移、readerId 指纹 span |
| 凭据 | 单个 41 字符 token | 133 字符 cookie 串 |
| 字体依赖 | 无 | 需随附替换字体表 |

实测样本中 App API 正文的 PUA 字符数与零宽字符数均为 0，且无 Base64 残留、无 HTML 标签。

**但上表最后一行的结论已经站不住了，记录在此以免后来者重复踩。** 2026-10 的复核发现两件事：

1. **PUA 字体水印是可反解的，且成本远低于估计。** 对三份真实水印字体（`exp/jjfont.ttf`、`jjfont_<novelId>_21.ttf`、`_22.ttf`）逐表比对：三者的 `glyf`/`loca`/`cmap` 表 MD5 各不相同（字形顺序被打乱、PUA 码位重新随机），但**单个字形轮廓的字节集合完全一致**（201 个，三者交集 201）。用其中一份已提取的映射构造「轮廓字节哈希 → 汉字」表后，回头解析另外两份的 cmap+loca，命中率均为 **200/200**。也就是说反解不需要光栅化、不需要参考 CJK 字库、不需要 IoU 匹配，只需一张约 1.4–3.8 KB 的常量表加一次 sfnt 表遍历。另外 WAP **免费章实测零水印**（PUA=0、ZWNJ=0、`@font-face`=0），三层水印只出现在 VIP 章。
2. **App API 有一个 WAP 没有的日常代价：它会把用户手机上的晋江 App 顶下线。** App token 由 `androidapi/login` 签发，看起来是单会话的。

配套的 Flash/RAM 复核（读 `firmware.map`，非估算）：GBK→UTF-8 表（`TxtEncoding.cpp.o` 47.7 KB）、wolfSSL AES（`aes.c.o` 10 KB）、FreeType（`ft_*.o` 139.9 KB）、`htmlEntities`、`ChapterHtmlSlimParser` **都已在镜像内**，改 WAP 的净增量约 −3 ~ +12 KB，而当前余量约 159 KB。**Flash 不是障碍。**

因此 WAP 从「不可行」变成「可行但未实现」。真正的前置阻断项是两条实验，都需要用户配合用手机观察，不能由固件侧单独确证：

- **E2（性价比最高，先做）**：App 登录的顶号是否由 `autologin=1` 或每次新生成的 `identifiers` 引起。若不顶号，整个 WAP 改造可以不做。
- **E1**：WAP `sid` 登录是否真的与 App token 独立。间接证据很强——WAP 登录页自带「点此向主设备申请验证」（`sendVerifyNotifyToMainDevice` / `askLoginRes`），即官方设计的二次验证方式之一就是让已登录的安卓 App 来批准；如果 WAP 登录会顶掉 App，这条链路自相矛盾。但**没有直接抓包证据**。

另有两点必须记住：`WeReadHttpClient` 没有 cookie jar、不跟随 302、只能 HTTPS，WAP 登录（POST→302→GET）要自己补；WAP 未购章返回的是一个 12 KB 的「点击购买」HTML 页，**没有任何数字 code**，所以拒读分类会从现在的「认 code」退化成「匹配 GBK 文案」——在 `statusFromCode()` 的 `default→Server` catch-all 已经三次掩盖真因之后，这一步必须先把诊断信息保留住再动。

接口分三个主机：`app-cdn.jjwxc.net`（免登录、HTTP）、`app.jjwxc.net`（业务 API、HTTPS）、`app.jjwxc.org`（登录、HTTPS）。请求携带 `versionCode`；章节接口在 `381` 下可直接返回正文，无需还原 APK 原生 `sign` 算法。

服务端返回有两层加密，均已实现并逐字节验证：

1. **整体信封**：响应体整体为 Base64 后的 DES 密文，密钥与 IV 由响应头 `accesskey`／`keystring` 派生。
2. **字段级**：信封内个别字段（如 `content`）在 `encryptType` 为 `"jj"` 时是第二层 Base64+DES。

两层都只使用对称算法，不涉及 RSA／ECC。字段级解密在解析阶段按流式进行，单章只保留约 40 字节状态，密钥扩展每章一次。

## 代码与数据

| 文件 | 职责 |
|---|---|
| `JjwxcActivity.*` | 界面、状态机、缓存／打包作业与取消 |
| `JjwxcHttpTransport.*` | 把 `jjwxc::Transport` 适配到 CrossMux 现有 HTTP 栈 |
| `JjwxcStore.*` | 凭据、免责声明、`toc.bin`（`JXT1`）与 `novel.bin`（`JXN1`）读写、路径、目录扫描、旧 TXT 清理 |
| `JjwxcEpub.*` | 章节 XHTML 流式生成、`nav.xhtml`／`content.opf` 生成、store-only ZIP 打包 |
| `lib/JjwxcApi` | 协议、URL 构造、流式 JSON 解析、三层解密 |

`JjwxcEpub` 复用 `lib/WeReadWebApi` 的公开组件而不另抄一份（这些组件在统一固件里始终编译，额外 Flash 开销为零）：`WeReadStore::StoreOnlyZipWriter`（store-only ZIP，中央目录落 SD 的 `central.part`）、`WeReadStore::IndexWriter`（12 B 头 + `.part` + 原子替换）、`WeReadStore::atomicReplace`、`WeReadStore::looksLikeZip`、`WeReadXhtmlCodec::writeLiteral`。**没有**复用 `WeReadClient` 里的 `writePackageFiles()`／`packageBook()`（文件内静态，且与 `WeReadStore::BookRecord`、`WRI2`/`WIP1` 图片工作索引、WeRead 的 `Error` 枚举耦合）和 `WeReadXhtmlCodec::sanitizeChapter()`（把整章塞进一个 `<p>` 用 `<br/>` 分行，并为 WeRead 的进度映射逐段插入 `<!--wr-co:N-->` 标记，JJWXC 用不上且会把每章体积放大数倍）。晋江正文无图片、无脚注，所以整个 `ImagePolicy` 子系统都不需要。

未购买／已锁定的章节写入由**该章自己的标题**加一句固定本地化说明组成的占位正文；每章各用一个 `ChapterWriter`、各写各的 `.part`，失败即整体丢弃，因此不存在把别章正文写进本章的路径。作业还会把响应里的章节名与目录里的标题对账，不一致时打 `LOG_ERR`，便于在真机上发现串章回归。

`lib/JjwxcApi` 内的 DES／MD5／Base64 为自带实现，不引入新的加密依赖。

HTTP 层直接复用 `lib/WeReadWebApi` 的 `WeReadHttpClient`，不新增第二套 TLS 客户端。它已实现固件所需的 HTTP/1.1 子集、按 Session 的连接复用（一批请求一次握手），并同时暴露正文回调与响应头回调——后者是读取 `accesskey`／`keystring` 所必需的。复用带来的额外 Flash 开销为零。

`JjwxcTransport.h`（lib 内，抽象接口）与 `JjwxcHttpTransport.h`（本目录，具体适配）刻意不同名，避免同名头文件在包含路径上的歧义。

### 内存

设备内部 SRAM 堆约 300 KB，实际可用仅数十 KB，且显示 DMA 需要预留 45 KB 连续内部 RAM——不足时屏幕变黑且**不报错**。因此：

- 所有网络与 SD 操作在一个绑定到 core 0 的工作任务中执行（12 KB 栈），UI 核持续 `yield()`，避免触发任务看门狗。
- 解析用 384 KB 缓冲区来自 PSRAM，不用内部 RAM，也不用栈数组。目录响应实测可达 73 KB（`\uXXXX` 转义未解码的线上格式约为解码后的 6 倍），栈上放不下，也会撑爆 ESP32 任务栈。
- 目录类接口（章节列表、书架、搜索）为 **SAX 流式解析，零缓冲**：明文响应直接喂给解析器，只有信封响应才需要暂存，且就地解码不另开第二份缓冲。
- 章节列表、章节状态、已下载书目三个容器都用 `jjwxc::PsramAllocator` 放在 PSRAM。1500 章的 `ChapterEntry` 约 216 KB，放内部 RAM 会在 `-fno-exceptions` 下直接 `abort()`。
- 章节正文**从不整章驻留内存**：`fetchChapter` 的流式回调直接喂给 `JjwxcEpub::ChapterWriter`，后者用一个 512 B 栈上缓冲批量落盘。打包是 store-only ZIP，等于纯 SD→SD 拷贝，RAM 成本只有调用方那 4 KB 缓冲（复用 384 KB PSRAM scratch 的一段，两者时间上不重叠）。
- `toc.bin` 的新旧合并是一次前向归并，只保留一条旧记录做前瞻，因此 4000 章的书目也不需要把 464 KB 旧索引读进内存。
- 下载进度计数为 `std::atomic`，跨任务读取无需加锁。
- 章节间固定 1500 ms 间隔，避免对服务端造成压力；命中缓存而跳过的章节不发请求，也不等待。

### 数据落盘

登录会话、章级缓存与元数据在 SD 卡 `/.crosspoint/jjwxc/`，成品 EPUB 在 `/JJWXC/`。字节布局见 [`docs/file-formats.md`](../../../../docs/file-formats.md#jjwxc-cache)。

- 凭据经 eFuse MAC 异或混淆后以 Base64 保存，不是明文，但也**不是加密**：它只防止 SD 卡被随手翻看时直接泄露，无法抵御持有同一设备的攻击者——设备自己必须能读回来，所以拿到这台设备就等于拿到密码。请妥善保管 SD 卡。默认**不保存密码**，只有在登录时显式选择「保存账号和密码」才会落盘。
- 会话与登录捷径是两个文件，故意分开的：`credentials` 是会话（token＋设备指纹＋昵称），退出登录时清除；`account` 是登录捷径（保存范围＋登录名＋可选密码），退出登录**不清除**，否则「用上次账号登录」永远只能用一次。两者都走同一套混淆。
- `autobuy` **已废弃，不再读取**：旧版本在这一位数字里存「自动购买策略」（`0` 询问／`1` 允许／`2` 停止）。策略连同 UI 一起删掉了（见上文「未购买章节」），卡片上遗留的这个文件不会有任何作用，也不需要清理。
- `<novelId>/toc.bin`（magic `JXT1`）每章一条 116 B 定长记录：`chapterId`、标题、`remoteSize`、状态（Missing／Cached／Unpurchased／Locked）、`isVip`、`localBytes`、`savedAt`。它就是增量缓存的依据：状态为 Cached 且文件在卡上且 `remoteSize` 未变的章节不再联网。已记为 Unpurchased 的章节**也不会**再被请求——重发一轮上百个请求要好几分钟，而在 App API 路径上那还可能再触发一次账号侧自动订阅；只有「重试未购买章」和「刷新缓存」会。
- `<novelId>/novel.bin`（magic `JXN1`）存书名、作者、封面 URL 与两个计数，供离线时的「已下载」列表和 OPF 元数据使用，也决定成品 EPUB 的文件名。**两个计数不可混用**：`cachedChapterCount` 只数有正文的章（可读），`packagedChapterCount` 数所有入包的章（含占位）。所有面向用户的「已缓存 N」都必须用前者。旧版本只写了一个（含义等于后者），`loadNovel()` 会识别并兼容，下次 `saveNovel()` 时自愈。
- `<novelId>/chapters/<chapterId>.xhtml` 是章级中间件；`cover.source.jpg` 是校验过魔数的封面原图，入包时按实际字节类型命名为 `cover.jpg`／`cover.png`。`cover.thumb.bmp` 是由它转出的 200×280 缩略图，**只有详情页读**，删掉只会多一次转换；封面原图重新下载时会一并删除，避免图片比原图活得久。
- 所有写入都走 `.part` + 原子替换，中断或断电不会留下半截正式文件；每次作业前先回收本目录下的 `.part`／`.bak` 残留。
- 首次运行新版本会一次性删除旧的 `/.crosspoint/jjwxc/books/`（`.txt`／`.meta`／`preview-*.txt`）及其 `txt_<hash>` 阅读缓存。该操作幂等，失败不影响启动，也不做迁移。

### 与阅读器的衔接

成品 EPUB 的路径不变而内容变化时，`book.bin`／`section.bin` 不会自动失效（它们只按路径取键，不记录源文件大小或修改时间），所以每次重新打包后都会清掉该书的阅读缓存。**只在本次运行是纯追加时**（新缓存的章节全部排在已入包的最后一章之后，且不是刷新）才把 `progress.bin` 搬回来：此时既有 spine 序号和分页都没有移动，阅读位置仍然有效；刷新或补齐中间缺章会改变分页，因此从头开始。生成或替换 EPUB 后还会调用 `library::markLibraryIndexDirty()`，否则新书不会出现在书架上——WeRead 没有做这一步。

### 为什么是 EPUB 而不是 TXT

早期实现把章节拼成一个 TXT，理由（TXT 管线已自带编码探测、中文章节标题识别、分页、书签、进度）本身没错，但它换不来可用的书架体验，实测结论如下：

| | TXT（旧） | EPUB（现） |
|---|---|---|
| 能否进书架 | **不能**。`LibraryBuilder` 整体跳过以 `.` 开头的目录，而旧产物在 `/.crosspoint/jjwxc/books/` | 能，成品在 `/JJWXC/` |
| 「最近阅读」条目 | 每个 `preview-<novelId>-<chapterId>.txt` 各成一条（Recent 以路径为键），一部作品裂成多本 | 一部作品一条 |
| 书名／作者 | 只能是文件名 stem；reflow 后写进 `book.bin` 的 title 也是文件名，language 硬编码 `en` | 从 `content.opf` 的 `dc:title`／`dc:creator` 读取，`dc:language` 为 `zh-CN` |
| 封面 | 拿不到。`ensureThumbnail` 只处理 EPUB／XTC；`cover.override` 对 TXT 分支提前 return | `cover.source.jpg` 以 `properties="cover-image"` 入包，首页主题能出缩略图 |
| 章节切分 | 依赖 `第N章 标题` 正文行被 `isChineseHeading()` 认出，写反顺序整本会被识别为单章 | 每章一个 XHTML，nav 平铺，切分是结构性的 |

因此现在改为 **累积式单产物**：章级缓存放隐藏目录，成品每次由**全部**已缓存章节重新打包（store-only，即纯 SD→SD 拷贝），书名、作者、封面、语言都来自书内元数据。

本轮把探索阶段验证过的七类能力接进了设备端。所有协议细节都来自真实会话实测，解析器在 `lib/JjwxcApi`，宿主测试在 `cpyos/src/`。

## 与书架、阅读器的衔接（2026-10-25）

- **更新快照**：App 每次成功拉完整本账号书架（未加收藏夹过滤）后，会把远端目录事实写进
  `/.crosspoint/jjwxc/updates.bin`（`JXU1`，32 B/本，上限 300 本，格式见
  [`docs/file-formats.md`](../../../../docs/file-formats.md#jjwxc-cache)）。书架、首页继续卡与阅读器只**读**这个文件，
  所以"这本书有没有新章"能在断网时回答——本项目不允许书架或阅读器自己拉起 Wi-Fi。
- **书架【同步】**：书架标题栏的刷新按钮现在做两件事——重扫卡（原有行为），以及在存在 WAP 会话时
  以子活动方式打开本 App 的 `RefreshUpdates` 深链，走一遍在线书架并把快照写新，然后立刻返回。
  网络部分必须在 App 里做：阅读器/书架自己的任务栈与内部 RAM 都不够一次 TLS 握手，而且失败的
  `connect()` 会把 UI 任务卡住一分钟。**快照过期时（从未同步过）显示"未知"，绝不显示"已是最新"。**
- **书架徽标**：封面网格右下角是来源单字（微/晋），右上角是落后章数；列表行副标题追加
  `· <来源> · N 章新`。
- **阅读器末页**：读到**最后一章最后一页**时，如果快照说卡上落后 N 章，页尾出现
  「还有 N 章 · 继续下载」，点击走既有的 `UpdateChapterList` 深链。这是连载书真正的"下一本"位置。
- **云端进度**：阅读器菜单里对晋江书不再显示 KOReader 的「同步进度」（那本书在 KOReader 上没有账号），
  改为「云端进度」，打开 App 的详情页——那里本来就负责读云端位置并写回本机位置。
- **未做**（明确决定，避免后人重开）：云端书架（书架里列未下载的书）不做；微信读书的划线/想法
  进正文不做；书架自动联网查更新不做。

## 设计约束

- **支付密码**：仅在 `JjwxcActivity` 内短暂保存，构建 POST body 后立即清空；日志只记录章节号与结果码。
- **进度同步**：只在登录态运行；先读云端再写本地，避免用旧设备位置覆盖手机新位置；云端章节必须在本机目录中才提供跳转行。
- **段评限流**：一个用户动作一个请求，最短间隔 1.5 s；不做后台预取，避免长篇逐段拉取放大请求量。
- **段评互动（2026-10-25）**：`JjwxcCommentActivity` 是阅读器和 App 共用的唯一段评面板。
  卡片底部有「赞 N」「回复 N」两个胶囊，点按直接动作；回复视图里只有「赞」和顶部的「回复」。
  新段评走键盘输入，正文上限 900 UTF-8 字节且不超过 300 字（站点上限）。所有写动作都要登录，且只在
  用户点按时发生；`code=10` 表示服务端要图形验证码，设备没有 JS，必须停手并提示去手机/网页完成。
  缓存格式升级为 JJD1 v2（保存 `commentId`、赞/回复计数与本人已赞状态），v1 仍可离线阅读，
  但旧行没有 id，只能刷新后才能互动。**请求主机仍是 `www.jjwxc.net`，不是 WAP 页面**；WAP 原生只有章评。
- **发现页**：匿名可用，不依赖 session；页面广告/活动条目通过「同 id 锚点 + novelname 优先」规则归一化为书名。

### 尚未验证

- 以上 UI 全部通过宿主测试与固件编译，**未在真机/模拟器上走查交互**；下一次上机应优先验证：发现页翻页、收藏夹增删改、云端进度跳转、购买密码键盘、段评两级列表、主设备批准的轮询与取消。
- `spine.bin` 只对**本轮之后重新打包**的书生成；旧书升级后第一次重新打包才会出现云端进度跳转。
- 双会话的常驻 TLS 内存代价未在真机测量（预计每条会话 10–20 KB 内部 RAM 量级）；若真机内存吃紧，可回退为单会话并接受握手开销。

## 验证状态

已通过（主机端，`-std=c++17 -Wall -Wextra -Werror`）：

- MD5 9/9 向量、DES NIST KAT、DES 往返 5/5。
- 信封密钥派生 3/3、整体信封解密 3/3（与 pycryptodome 结果逐字节一致）、就地解码 3/3、内层字段 3/3。
- 章节列表解析 23/23：对真实抓包在 1/7/64/1024/2047/4096/整块 七种分块尺寸下结果一致，40 章、18 章 VIP、章号单调递增、取消在分块边界停止。
- 联机测试 12/12（真实服务端）：章节列表、作品信息、免费章 9617 B、**VIP 章 29887 B（PUA=0、零宽=0）**、书架 12 本。

未验证：

- 真机端到端行为（构建通过后需在设备上验收），尤其是：生成的 EPUB 能否被内置阅读器打开、nav 章节跳转是否正确、封面缩略图能否出现在首页主题、`/JJWXC/` 下的成品能否进书架与「最近阅读」。
- 打包与增量缓存的性能。store-only 全量重打包的耗时随已缓存总字节数线性增长，一本几 MB 的书预计是数秒级的 SD 拷贝，但没有实测数字。
- 追加式打包后 `progress.bin` 的搬运是否真的让阅读位置无缝衔接（设计上 spine 序号与分页都不变，但只有真机能确认）。
- 目录规模上限。4000 章的书目列表为兆级响应，流式解析在设计上不受长度限制，但未在真机上跑过；`toc.bin` 会是 464 KB，打包时对它的三次遍历也未实测。
- 封面下载。`NovelInfo::coverUrl` 的主机是否提供 TLS 未确认；固件的 HTTP 客户端不能说纯 HTTP，所以 `http://` 的封面 URL 会被改写成 `https://` 再试，失败则本书不带封面（不影响其余功能）。
