## What it is

A phone-shaped reading browser: fetch one HTTPS page, strip it to a linear
reading document, paginate it with the UI font, and expose its links. It is
meant for text-heavy pages (novel chapters, articles, old-school WAP/HTML
sites), not for web applications.

Non-goals, each with a reason:

| Not supported | Why |
|---|---|
| JavaScript | No JS engine fits the remaining flash; see the TactileBrowser analysis. |
| Images | The layout engine has no inline image flow; `<img>` text (alt/title) is dropped. |
| Plain HTTP | `SecureClient` is HTTPS-only. `http://` is upgraded to `https://`. |
| Gzip / brotli | No `Accept-Encoding` is sent; a gzip response is reported as unsupported rather than fed to the tokenizer. |
| Forms / login | No cookie or form model; the browser never authenticates. |
| IDN host names | Non-ASCII hosts are rejected instead of being sent as raw bytes. |

## Pipeline

```
WeReadHttpClient (wolfSSL, TLS 1.2/1.3)
  -> 2 MiB PSRAM body buffer, 1 MiB markup cap, redirect loop (5)
  -> charset: Content-Type -> <meta> -> detect() -> GBK/UTF-16 transcode
  -> lib/WebBrowser/ReaderExtractor: tolerant tokenizer -> linear blocks + links
  -> lib/WebBrowser/TextPager: CJK/Latin wrapping -> lines -> fixed-height pages
  -> WebBrowserActivity: CPY shell, page turns, link underlines + picker
```

The fetch runs in a dedicated task (`webFetch`, IDLE priority, core 0, 96 KiB
PSRAM stack) for the same reason as the JJWXC app: the wolfSSL handshake needs
internal RAM the UI task must keep, and a CPU-bound handshake at a higher
priority starves IDLE0 and trips the task watchdog. `WifiPowerSaveGuard` holds
240 MHz for the duration; `background_work::Guard` keeps standby from
light-sleeping mid-fetch.

## Known limitations

- Body text is drawn 1-bit with `UI_10`; it does not use the reader's 16-level
  AA path yet. Body font size follows the UI font, not the reader setting.
- A line may be a few pixels wider than measured when per-glyph fallback
  changes face mid-line; the content clip and a 6 px safety margin absorb it.
- Heading lines are measured regular and drawn bold, so they can be clipped at
  the right margin.
- Cancelling a fetch waits for the request to time out (30 s) because the TLS
  client cannot abort a blocking connect; `onExit` waits up to 35 s.
- History is RAM-only and bounded to 32 entries; no address bar history UI.
- The link picker shows at most 8 unique links on the current page.

### What works on the device

- **Fetch**: silent connect to the last saved network (setMode → BLE stopped,
  memory reclaimed), 12 s first-attempt timeout + one 2.5 s-delayed retry over a

### Why the first fetch used to reboot the device

```
assert failed: udp_new_ip_type ... (Required to lock TCPIP core functionality!)
runFetch -> WeReadHttpClient::request -> SecureClient::connect
        -> NetworkClient::connect -> NetworkManager::hostByName
        -> dns_clear_cache -> dns_call_found -> sntp_dns_found
        -> sntp_request -> dns_gethostbyname -> udp_new_ip_type
```

Arduino's `hostByName()` clears the DNS cache when the interface's global IP
state changes (the first lookup after association), and lwIP runs pending DNS
callbacks in the caller's thread. SNTP was started by the Wi-Fi page seconds
earlier, so the flush failed its lookup and SNTP retried a cold DNS request from
our PSRAM task, hitting the missing core lock. Fix: `WifiSelectionActivity` has
`syncTimeOnConnect` (default true); the browser passes false. Do **not** add a
custom `getaddrinfo` warmup: measured on this device it made later resolutions
fail (EAI_FAIL) even though the host resolved from a PC on the same LAN.

### Why pagination was 20 s and lines overflowed

Two separate mistakes:

1. Measuring every character through the renderer walks compressed font groups
   (~50 ms for one whole CJK line, ~3 ms per glyph). A 200-line chapter spent
   10-20 s in pagination.
2. Per-glyph measurement and whole-line drawing could resolve **different
   fallback faces**, so the measured line was up to 23 % narrower than the drawn
   one and the page overflowed the right edge.

Fix: the pager uses a glyph-width model — ASCII widths measured once, CJK uses
the face's single advance (sampled once), spaces use `getSpaceWidth`, everything
else memoised. Draw and measure use the same body face. Whole-line verification
(`PagerSpec::verifyWholeLines`) remains available for tests and is off in the
product. Pagination is now 61-150 ms for a page of text (409 ms first time while
the model calibrates).

### Transport: HTTPS and plain HTTP

- The fetch worker uses `freeink::SecureHttpClient`, which speaks both schemes:
  https runs over wolfSSL (`SecureClient`), plain http over the WiFiClient
  transport. The old `WeReadHttpClient` path was HTTPS-only, which is why the
  browser used to upgrade every `http://` to `https://`.
- An explicit `http://` is now kept and shows a one-time `HTTP 明文（不安全）`
  toast. A bare host still defaults to `https://`, so plain HTTP is opt-in.
  Redirects may switch schemes; the caller resolves Location with `WebUrl` and
  follows up to five hops.
- Header framing (Content-Length, chunked, close-delimited), keep-alive and the
  abort callback are handled by `SecureHttpClient`; the browser keeps its own
  1 MiB body cap, gzip inflate, charset detection and reader extraction.
- NetworkManager clears the lwIP DNS cache on the first resolve after an
  association. If SNTP has a DNS query pending at that moment, its callback runs
  on the browser's task and `udp_new_ip_type` asserts (lwIP core locking). The
  browser therefore pauses HalClock auto-sync and stops any running SNTP before
  navigating, and restores the user's setting on exit. This is what fixed the
  `udp_new_ip_type` crash on first navigation after a clock sync.

### Touch-first chrome, progress and retry

- The browser follows the CPY touch convention: no hand-rolled footer text.
  The header carries the system back disc (tap = Back), the address pill has
  the globe icon, and the only bottom-bar items are a bordered "Menu" pill and
  the page counter. `GUI.drawButtonHints()` is still called for button-only
  boards; `buttonHintsVisible()` hides it on touch.
- Error pages use `GUI.drawActionButton` pills: a filled Retry and a bordered
  Back, both hit-tested from `loop()`; Confirm/Back still work.
- Back is page -> URL -> browser start page -> system home. Page 1 of the first
  URL returns to the in-app Home (address pill, bookmarks/history, recents)
  instead of leaving the app, so the start page is always one Back away.
- Loading is one continuous, monotonic bar for the whole navigation: Wi-Fi
  10-25 %, connect/wait 25-45 % (time-weighted while the transport cannot report
  TLS progress), body 45-95 % (real received/Content-Length when known, or
  received bytes), formatting 95 %, then the page replaces the card. Every term
  only moves forward, so the duck never swims backwards. Details show "42% ·
  1.2 / 3.4 MB", "7.0 KB", or sub-KB bytes instead of rounding 7 KB down to
  "0 KB". The card refreshes about once per second.
- The fetch holds `HalPowerManager::Lock` (240 MHz) for association and the
  request. Without it the idle governor drops to 80 MHz and Cloudflare-fronted
  pages take tens of seconds. `setReuse(false)` closes each request rather than
  leaving a half-open keep-alive, and up to three attempts are made 1.5 s apart
  (90 s for the first, 60 s after that). The UI deadline is 240 s, so a large
  but progressing page no longer hits a short ceiling. After 4 s without a
  response byte the card says "waiting for the server" instead of counting
  seconds, and after 20 s "network is slow".
- Decompression: gzip is detected from the bytes even when the header lies (a
  proxy that strips the body but keeps `Content-Encoding: gzip` used to produce
  "unsupported encoding"); `deflate` is accepted as zlib-wrapped or raw; a
  compressed stream cut by the 1 MiB body cap, or an output buffer that fills,
  is shown as a truncated page instead of an encoding error.
- Cloudflare-fronted hosts (52shuku) tarpit this device's TLS client: the first
  response byte has been measured at 20-35 s even though the host gets the same
  page in ~1.5 s. The fetch now survives that window and shows received bytes;
  it is a server/TLS-fingerprint delay, not a paginator stall.

### Superseding an in-flight request

Choosing another link (or typing an address) while a fetch is still unwinding no
longer shows "the previous request is still finishing". `navigateTo` marks the
old job abandoned/cancelled, remembers the new URL (and whether it should push
history), and keeps the wait card on the new host. `loop()` starts the queued
fetch as soon as the old worker is reaped; a rapid sequence of links replaces
the queued URL instead of stacking fetches. Back/Cancel clears the queue.
Verified on device: slow 52shuku link, Cancel, then example.com 1 s later loads
without the BUSY toast.

### Hit targets on a touch panel

- The reading page bottom bar is chrome: a 120x50 Menu pill with 8/10 px of hit
  padding, the page counter, and a rule that taps below the text column never
  turn a page (`ty >= height - kFooterHeight - 60`). Edge turn zones are the
  outer 22 % (were 30 %), so a near-miss on the pill or the text centre no
  longer flips a page.
- Link hit rectangles are widened by 4 px on each side and 6 px below the line,
  and links are tested before the bottom-band/page-turn rules, so tapping an
  underline no longer falls through to a turn.
- While a body trickles, the card updates the byte count every second and adds
  "waiting..." after 2.5 s without a new byte; a 5 s heartbeat log prints
  `body N/M after X ms` so a stalled transfer is visible in the serial log.

### Places: bookmarks and history (persisted)

- Storage: `/.crosspoint/browser/bookmarks.txt` and `history.txt`, WPL1 text
  (`WPL1\t1`, then `url\ttitle\tvisitedAt\tpage`), tab/newline escaped.
  Writes go to `<file>.tmp` and `WeReadStore::atomicReplace`; caps 50 records
  each, history ordered MRU first and deduped by normalised URL.
- History is written on leaving a page (Back to the previous URL, menu Home,
  app exit) and every 10 page turns; `page` is the 0-based page that was read.
- The page menu (Up) has Address / Reload / Add-or-remove bookmark / Bookmarks /
  History / Home. Add-or-remove keys on the current URL and records the page.
- Bookmarks and history lists share one renderer: title + host + page + date,
  a selected-row bar, a tail trash button (inline confirm, Cancel focused) and
  an Up menu with Delete / Clear all. Opening an entry refetches the URL and
  restores the saved page; if the document is shorter now, it clamps to the
  last page and shows `页面已变，已跳到开头`.
- Back semantics are page -> URL -> exit. A failed navigation keeps the old
  document; Back closes the error card and restores the previous URL (the
  failed URL is popped from the URL stack).
- The offline fixture (`example.invalid`) is never written to history.

### Known limitations / open items

- **TLS is still `setInsecure()`** (`WeReadHttpClient` does this for every
  caller). The planned SD CA bundle + clock check is not implemented; until
  then the browser is not safe against a MITM.
- **The earlier "only example.com works" result was our bug, not the network.**
  The failing sites were caused by three deviations from the proven
  `JjwxcHttpTransport` path: a custom `getaddrinfo` DNS warmup before the
  request, a 12 s first-attempt timeout, and a fresh `Session` per fetch. The
  browser now mirrors JJWXC: no DNS warmup, a persistent `Session` reset at job
  start, a 45 s timeout and a 1 s settle after association. Verified on device:
  jjwxc chapter 1/2 (GBK + gzip), gutenberg.org and baidu.com all fetch.
- **Activity teardown order matters**: destroying the persistent TLS session
  after `releaseRadio()` panicked with `InstrFetchProhibited`. Reset the session
  first and only release the radio if this activity brought it up
  (`wifiSessionActive_`), exactly like `JjwxcActivity::onExit()`.
- No images, no forms/login, no JavaScript, no IDN, no gzip brotli/zstd.
- The URL stack itself is RAM-only (32 entries); bookmarks and history persist.
- The browser never opens the Wi-Fi picker or the Wi-Fi UI. It tries the last
  saved network for up to 15 s behind the shared wait card; on failure it shows
  the offline error page, releases the radio and lets Back return/exit. A failed
  navigation keeps the loaded document and floats the reason over it.
- Body font follows the reader point size; it does not yet expose a separate
  browser font size.
