# 脆皮鸭 CPYOS 0.8.4

Read Pico `0.8.4-rp` · Metalio E-INK4 Plus `0.8.4-e4p`

本次是**发布打包修复**：应用固件行为与 0.8.3 相同，修的是 0.8.3 发布资产里
**两个设备的数据包同名互相覆盖**。

## 修复：Plus 与 Read Pico 的数据包在同一个 Release 里重名

0.8.3 的两个设备作业都按 manifest 的构建文件名把数据包上传到同一个 Release：

| 数据包 | Read Pico | Plus | 大小 |
|---|---|---|---|
| `i18n_pack.dat` | `6e4a4441…` | `3d512953…` | 354,380 B（**完全相同的大小**） |
| `web_pack.dat` | `9f74a214…` | `a65ac776…` | 124,263 B |

四个包（pinyin / hyphenation / emoji / 阅读核心）两目标逐字节相同，不受影响；这两个不是。
结果是 Release 上只剩下**最后上传的那一份**：i18n 是 Read Pico 的、web 是 Plus 的。
按摘要校验的安装器会拒绝这个包；不校验的安装器会把另一目标的字节写进设备——语言包在
启动时被判为「键集/内容签名不符」并回退英文，网页资源包可能落到恢复页，而两者看起来都像
「更新已安装」。

## 修复方式（结构性，不是两个特例）

- **Plus 的每个数据包都以 `plus-<构建文件名>` 发布**（`plus-i18n_pack.dat`、
  `plus-web_pack.dat` …），Read Pico 保持原名。两套命名**不可能再相交**，即使将来第三个包也
  分叉。
- `scripts/plus_release_bundle.py` 负责暂存：逐个数据包与 manifest 里的**大小 + SHA-256**
  比对，不一致直接让作业失败（0.8.3 的成因就是两个目标的包被混在一起），复制后再校验一次，
  并把发布版 `data_manifest_plus.txt` 的路径列改写为暂存名。
- `flash_plus_data.py` 现在**优先在 manifest 旁边**找数据包，所以下载一个发布包即可
  `python3 flash_plus_data.py --manifest data_manifest_plus.txt`（以前它只认仓库里的 `build/`）。
- 网页刷机清单（`flash-plus.json`）从发布目录取 manifest 列出的文件名，自动跟随前缀。

## 门禁

- 新增 `scripts/tests/test_plus_release_bundle.py`：断言 Plus 名与 Read Pico 名**不相交**、
  暂存后的 manifest 指向暂存文件、**摘要不符时必须拒绝**（并带上是哪个包）；两个发布作业在
  打包前都会运行它。
- 仓库内的 Plus manifest 与本机构建产物也要一致；本机只有 Read Pico 构建时会跳过这条
  （那里的 Plus manifest 不是权威来源）。

## 升级建议

- **Read Pico**：0.8.3 的固件与数据包本身没有问题（它的 i18n/web 就是 Release 上留着的那份），
  可继续用 OTA。
- **Plus**：如果你在 0.8.3 之后**从 Release 下载数据包手工刷过数据分区**，语言可能已经回退成英文、
  或网页显示恢复页——用 0.8.4 的 `plus-*.dat`（或网页刷机）重刷一次数据分区即可；
  数据库（书籍、设置、进度）不受影响。
- 固件行为、分区布局、数据包格式与 0.8.3 相同，**不需要**整片擦除。
